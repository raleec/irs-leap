BUILD OUTCOME
An internal, licensed employee enters one category and one calendar day per
request, selects one to three internal approvers, and optionally supplies whole
number hours. Dataverse records the authenticated requester and year of leave.
One native Approve/Reject - First to respond approval is assigned to those users.
A selected responder's first valid decision is written by the automation account;
the server stamps the decision time. Other approvers then see the terminal state.
The app shows a 42-cell month date picker and an authorized selected-day list.
Annual totals come from the secured server API, never a sum of visible rows.

NON-NEGOTIABLE BUSINESS RULES
1. Exactly one category per request, using the 13 labels in Snippets\00-Contract.txt.
2. One date per request. Start Minute is 0..1439; End Minute is 1..1440 and must
   exceed Start Minute. End 1440 means 24:00 at the END of the selected day, not
   the next day's 00:00 as a second date. Cross-day leave requires separate rows.
3. Leave Hours is OPTIONAL and independently entered, integer 0..24. Blank means
   unknown; zero means explicitly zero. Do not infer hours from elapsed minutes.
4. Multiple requests on one day and overlapping intervals are permitted. Do not
   add uniqueness or overlap-rejection logic to the app, flow, or table.
5. Annual total means approved recorded hours for the YEAR OF LEAVE, not the
   year of approval. Overlapping approved records each contribute their hours.
   Approved blanks contribute zero known hours AND increment MissingHours;
   approved explicit zeros contribute zero hours without incrementing MissingHours.
6. Requester/owner, Calendar Year, status, and decision stamps are server-owned.
   There is no employee edit/delete/cancel or direct Canvas decision Patch.
7. Lookup selection does not grant a license, provision a Dataverse user, or
   create security privileges. Onboard the internal user FIRST.

STAGE 1. FRAME THE MODEL AND IDENTITIES (20 MINUTES)
SAY
"A row is a request, not a person-day. Two rows can share a date and even overlap.
Hours are entered facts; no hours is not zero. Annual means the leave date's year."
DO
1.1 Draw E -> Dataverse create -> F's create-only flow -> A/B native approval ->
    F's status update -> server stamp -> E's generic result email.
1.2 Explain identity boundaries: the Canvas Dataverse connection runs as the
    signed-in user; the flow Dataverse connection runs as F; an approval responder
    is separately validated against the original request's selected users.
1.3 Demonstrate a synthetic Approved row with blank hours, one with 0, and two
    overlapping Approved rows with 2 and 3 hours. Expected known total is 5,
    approved request count is 4, missing-hours count is 1.
1.4 Open the same date as E, A, and U using separate browser profiles. Explain
    why a calendar can show different authorized rows to different people.
PASTE
Nothing. Use 00-Contract.txt as the on-screen contract, not a hard-coded local
collection masquerading as Dataverse data.
EXPECT
Participants can state who creates, who decides, and why visible rows cannot
be the input to an employee-wide annual total.
CHECKPOINT
Ask: "An October leave request approved next January belongs to which year?"
Answer: October's calendar year. "Blank vs zero?" Unknown vs explicitly zero.
RECOVERY
Resolve the data semantics now. Do not implement inferred duration, one-row-
per-day constraints, a single all-employee cache, or delegated-flow identity.

    API inputs: RequesterId is Text(varTotalsRequester.User); CalendarYear is an

STAGE 5. BUILD THE NATIVE APPROVAL FLOW (80 MINUTES)
SAY
"Email/native approvals is our supported baseline. First to respond means one
approval assigned to several selected people, not three separate approvals."
DO
5.1 Save the app so its Details page provides a web play link. Copy the actual
    same-cloud play URL. Keep it private to the workshop; do not paste a maker
    edit URL or a commercial-host link into a GCC flow.
5.2 In the SAME solution, New > Automation > Cloud flow > Automated. Name it
    LEAP - Request approval. Select Microsoft Dataverse trigger When a row is
    added, modified or deleted. Set Change type = Added; Table name = LEAP
    Requests; Scope = Organization. No modified trigger and no OData filter on
    status. Trigger Organization scope controls event coverage, NOT app security.
5.3 Use F's connection references for Dataverse/Approvals/Outlook. Make F a flow
    owner with the minimum privileges required by the starter, not a shared
    administrator credential. Do not add every participant as flow co-owner.
5.4 Open trigger Settings. Leave Concurrency Control OFF. In particular, do not
    set Degree of Parallelism = 1 for a flow waiting up to seven days: that
    serializes all employees behind the first pending request. This does not
    mean per-row duplication is solved; see Stage 6.
5.5 Open 50-Flow-Build.txt and implement every action in order. Rename each action
    exactly as shown BEFORE pasting expressions from 51-Flow-Expressions.txt.
    If the new designer hides an input, use Add new parameter/advanced parameters.
    Use Expression/fx to paste expressions without @{...}; interpolation syntax
    is only used in plain text fields, and these examples avoid relying on it.
5.6 The flow builds an array from saved Approver lookup GUIDs, removes blanks,
    and Lists the corresponding Users rows with systemuserid equality clauses.
    It never sends to free text entered by an employee. It validates the exact
    selected set against enabled users and the approved internal cohort, Selects
    Entra GUIDs, union-deduplicates, then joins with semicolons.
    Native approval Assigned to supports Entra user GUIDs as well as email/UPN.
    Entra GUID assignment avoids UPN/SMTP mismatches. An unusable account is an
    explicit operational error, not silently removed from the selected set.
5.7 Use Standard approvals > Create an approval:
    Approval type = Approve/Reject - First to respond;
    Enable notifications = Yes; Enable reassignment = No.
    Persist the returned Approval ID on the request BEFORE Wait for an approval.
    This is ONE approval, split into create/wait so its durable ID can be saved.
    Do not additionally add Start and wait for an approval, which creates a
    second independent approval.
    IMPORTANT: create/save/wait has a documented immediate-response race. A
    response before Wait registers can be missed even though the native service
    completed the approval. Reconcile using the saved ID; do not declare every
    response timing safe. Files 52 and 60 require this negative/race rehearsal.
5.8 On Wait for an approval set Timeout = P7D in action Settings. Seven days is
    intentionally shorter than the standard platform run-duration limit; verify
    current tenant/platform constraints in rehearsal. Use PT2M only for the
    timeout test and restore P7D before handoff. Timeout does not necessarily
    remove the native approval from clients; the terminal Dataverse status is
    authoritative and late replies must not change Expired.
5.9 Validate the returned responder ID (preferred) or, only when ID absent, email
    against the selected Users rows; map the matching row to its Dataverse
    systemuserid for Decided By. Do not write the Entra GUID into a User lookup.
    Switch Outcome on case-sensitive Approve / Reject. Unknown, empty, or
    malformed response -> Processing Note + administrator recovery, NOT Denied.
5.10 Use Dataverse Update a row for leap_status and Decided By/Decision Comments
     on the matching Pending request. Send ONLY these transition fields. Do not
     include Processing Note or Approval ID in the transition. The guard permits
     workflow-only writes while Pending and a separate terminal transition.
     Do not set Decided On; server stamps it.
     Use the custom Request Status field, not built-in Status or Status Reason.
     A read-then-update guard is not an atomic compare-and-swap; the plug-in's
     guard is not a proven race-safe backend or exactly-once dispatcher.
5.11 Send the requester only request ID, terminal status, and app URL through
     Office 365 Outlook > Send an email (V2). Do not echo Title, Description,
     category, comments, health/RA details, hours, or other employees. Email
     failure after a successful decision must not cause a new approval.
PASTE
50 and 51 provide every action, branch, lookup binding, and expression.
EXPECT
E saves a request -> a run begins -> selected A/B receive one native approval ->
one selects Approve or Reject -> row reaches Approved or Denied with selected
Decided By and server Decided On -> E receives generic result email.
CHECKPOINT
Create two different Pending requests before responding. Verify BOTH flows
reach Wait concurrently. Confirm one has three optional-recipient cases tested
(one approver, two, three) and no blank semicolon entries or duplicate recipients.
RECOVERY
No run: confirm flow On, environment, Added trigger, Organization scope, F
privileges, and trigger registration. No approval email: inspect Create action
and Approvals portal, mailbox/DLP, connection cloud, and selected provisioned
users. "User not found" is not solved by changing to a global directory picker.
If approval output schema differs, inspect the synthetic run's raw output and
bind the equivalent actual Approval ID/Outcome/Responses tokens. Never treat
an unknown token as Reject. Document the rehearsed mapping for the class.

STAGE 6. TIMEOUT, FAILURE, DUPLICATE, AND OPTIONAL TEAMS (45 MINUTES)
SAY
"The platform delivers events at least once. Our saved-ID guard reduces ordinary
replays; it is NOT an exactly-once dispatcher or a durable atomic outbox."
DO
6.1 Add the Scope_Expire and failure branches exactly as 52-Flow-Recovery.txt.
    Use Configure run after/Settings > Run after in the designer. Timed out,
    Failed, Skipped, and Succeeded are different statuses: select only the
    ones stated. A skipped Wait because of a preparation failure is NOT expiry.
6.2 Scope_Expire gets the row AGAIN, verifies Pending and the same Approval ID,
    and updates ONLY custom Request Status to Expired. No Processing Note,
    Approval ID, Decided By, or Decided On is included in that update. A skipped
    Wait must never enter this branch. A timed-out Wait does not establish that
    the service received no immediate response; use the saved-ID reconciliation
    procedure and record this timing limitation.
6.3 A generic failure note is concise and non-sensitive. Alert only the approved
    operations mailbox, with request ID, run ID, and app link. Do not dump action
    outputs or medical text into email/logs. Follow the decision/notification
    separation in 52: notification failure does not undo a valid decision.
6.4 Run the PT2M timeout rehearsal and restore P7D. Submit an approval afterwards:
    the row must remain Expired, and neither an ordinary user nor an old flow
    run may overwrite the terminal state.
6.5 Resubmit a synthetic completed run from Run history only in rehearsal.
    Approval ID/status guard must stop before Create an approval. This test does
    not establish race safety: two executions can both read a blank ID before
    either writes it. Also, creation may succeed before ID persistence fails.
    Never blindly resubmit that ambiguous run; inspect the Approvals service.
6.6 Explain production hardening: atomic per-request dispatch claim with unique
    key/outbox state, durable Approval ID correlation, idempotent decision writes,
    row-version/atomic transition control, retry/reconciliation workers, monitoring,
    least-privilege identity lifecycle, and cancellation/expiry reconciliation.
    The starter does not claim to supply this full outbox. A production release
    needs an engineered and tested implementation, not a trigger concurrency=1
    workaround or a text "Processing" marker treated as a lock.
6.7 OPTIONAL, only after baseline succeeds and time remains: make a SEPARATE
    manual test flow, not part of the approval decision path. Use Microsoft Teams
    > Post message in a chat or channel, Post as = User, Post in = Channel, and
    choose a permitted STANDARD test channel where F is a member. Post only
    "Synthetic LEAP workshop notification test - no action required."
    Run once with approval from the workshop owner in the target tenant, then
    record the connector operation, User poster, successful run, and receipt.
    This guide itself sends nothing. If not tested/allowed, record NOT VERIFIED
    and omit the feature. Do not post individual leave details to a team channel.
    Flow Bot is unsupported in GCC/GCCH/DoD; the official connector reference
    directs government tenants to use User instead. A connector appearing in the
    catalog is NOT proof that a particular poster/action/channel is supported.
    Do not use adaptive-card-and-wait as the workshop's approval engine.
PASTE
52-Flow-Recovery.txt supplies the run-after matrix and repair actions.
EXPECT
Timeout is a distinct Expired status; failure is diagnosable without silently
denying leave; duplicate replay does not intentionally create another approval.
CHECKPOINT
Show timeout proof, a controlled failure note, and the replay guard. Clearly mark
the unresolved concurrent-delivery/dispatch-gap limitation in the handoff.
RECOVERY
If a pending approval has an ID, reconcile/wait on THAT ID. Do not clear it and
send again. If status already terminal, repair only notification delivery and
keep operational notes in the approved support/audit record OUTSIDE the row.
The guard rejects Processing Note updates on finalized rows, even from F.
Never reopen/delete the original audit row or attempt to append a terminal note.
When mail delivery fails, a native Approvals portal response is an allowed
baseline fallback. A custom email cannot itself become an actionable native
approval. If a selected responder cannot be validated, stop and investigate.
