Important behavior
------------------
- One calendar date and exactly one category per request.
- Leave hours are optional whole numbers from 0 through 24.
- Blank hours are not estimated and are not the same as an explicit zero.
- Overlapping requests and multiple requests per day are allowed.
- Annual totals sum approved entered hours independently, including overlaps.
- Totals use the year of the leave date, not the year of the approval.
- The requester and their assigned approvers can see annual aggregate totals.
- Aggregate access does not grant access to unrelated individual requests.
- Submitted requests are immutable in this MVP.
- Approved/Denied are final decisions; edits and cancellations are not included.
- The calendar is a month/day view, not a pixel-for-pixel calendar-matrix clone.

Approval ID deliberately remains EMPTY in this core path. Start-and-wait does
not return its result until the wait completes, so the core cannot persist an
ID before responses. The current guard does NOT require Approval ID for a
selected-user decision. No core action writes it or Processing Note. Do not add
a late "Save Approval ID" to a terminal update; the guard rejects that payload.
The advanced split pattern offers different correlation/recovery tradeoffs;
its immediate-response risk and extra actions are not part of this core lab.

The Added trigger targets one flow run per create in the normal path, NOT an
exactly-once delivery guarantee. Duplicate trigger deliveries, ambiguous connector
dispatch failures, manual resubmission, and retries can create duplicate native
approvals. Retry None reduces automatic redispatch; it does not prove no send.
Pending checks and server terminal guards do NOT prevent duplicate dispatch or
provide an atomic first-writer claim across runs. Do not claim production safety.
Native First to respond arbitrates the single approval's result, not duplicates.

Have the authorized operator monitor FAILED/TIMED-OUT runs during the lab.

send the ScopeWaitFailure email. Preparation, decision-write and notification
failures also require run-history review, even if no administrator email arrives.

The generic admin email contains no raw errors or serialized connector outputs.

any retry; never blindly Resubmit the flow or create another approval.
If only the result mail failed, inspect saved status and resend only that generic
notice under the approved operations process. Do not rerun the approval.

do not fabricate Denied, write exception text into the request, or bypass security.

Security and immutable workflow contract
----------------------------------------
Requesters and every selected approver must be enabled internal Dataverse
systemusers with an Entra object ID, a nonblank non-guest domain name, no
application ID, and an interactive access mode (0, 1, or 2). Self-approval and
duplicate selected users are rejected. Approver 1 is required; 2/3 are optional.

On Create, the guard derives requester and owner from the initiating caller,
forces Pending, derives the year, and clears workflow-managed fields. Supplying
non-null workflow-managed fields on Create is rejected. Submitted requester
and owner values are not trusted; they are overwritten.

Content, date, hours, approvers, ownership, requester, and derived year are
immutable after save, including while Pending. Even same-value attribute
writes are rejected. Assign is blocked. Finalized requests (Approved, Denied,
Expired) are immutable in their entirety: no approval ID, processing-note,
comment, or status changes are accepted afterward. Correct data before
submission; this source does not implement amendments or reopening.

Pending workflow updates require the initiating caller to have a direct or
team-inherited role named exactly IRS LEAP Automation or System Administrator.
This is a TRUSTED AUTOMATION boundary. A normal selected approver cannot update
a request directly merely because they received a read share. The trusted flow
must authenticate its approval response and submit the selected approver in
leap_decidedbyid. The plug-in validates selection and user eligibility, but it
does not independently verify an external approval response or prove that the
attributed approver personally submitted that response.

While Pending, automation can write leap_approvalid and leap_processingnote.
A final Approved/Denied update requires leap_decidedbyid to identify a selected
approver, accepts optional decision comments, and stamps leap_decidedon in UTC.
Do not send leap_approvalid or leap_processingnote alongside finalization;
persist those earlier while still Pending. Expired clears decision attribution.
Never submit leap_decidedon or leap_year from the flow; they are server-managed.

Use least-privilege Dataverse roles in addition to plug-in validation:
employees need request Create, own-row Read, and necessary lookup Append/
AppendTo and internal-user directory Read privileges; approvers need table Read
privilege for their explicitly shared rows. Do not give ordinary users table
Delete, Assign, Share, or organization-wide request Read/Write. Automation needs
the workflow access it uses and the trusted automation role, not an employee's
interactive session. The plug-ins do not guard Delete, so deny Delete through
roles. Restrict who can assign the trusted role or modify/disable registration.
Validate actual security-role depth and lookup privileges in the target tenant.

Annual totals and privacy scope
------------------------------
The requester can obtain their own totals. A selected approver on ANY saved
request for that requester can obtain that requester's totals for ANY accepted
year (1900..2100). This is lifetime selected-approver authorization: the
authorization query intentionally has no year or status filter and no expiry.
A current-year selection is not required. Do not describe it as authorization
only for one request, one year, or currently Pending requests. If that lifetime
scope is unacceptable, change the design and retest before deployment.

The elevated aggregate includes only Approved rows for the requested requester
and derived calendar year, across rows the caller may not otherwise read.
It counts approved requests, sums explicitly recorded leap_hours, and counts
non-null hours. MissingHours = ApprovedRequests - non-null-hours count.
An explicit zero is recorded; blank is missing. No approved hours are inferred
from interval duration, and overlapping requests are allowed.
Dataverse aggregate errors/record-limit faults fail the operation rather than
returning a partial sum or paging ordinary records. The normal aggregate query
record limit is 50,000 matching rows and is an environment/service constraint.

Reliability boundaries
----------------------
The Create guard and approver sharing are transactional in Dataverse. There is
NO atomic outbox linking Dataverse Create to Power Automate or external approval
creation, and NO concurrent compare-and-swap guarantee in these plug-ins.
An immutable finalized-row check does not by itself prove first-response-wins
under concurrent final updates. A stored approval ID also does not close the
crash window between creating an external approval and saving that ID.
Use appropriate flow serialization/idempotency/reconciliation and platform
conditional writes where required; prove the complete orchestration separately.
Do not claim exactly-once delivery, guaranteed CAS, or external atomicity.

THE CREATE / SAVE / WAIT IMMEDIATE-RESPONSE RACE
Create an approval returns before Wait for an approval subscribes. An approver
can click immediately during ID persistence. The approval service can complete
while Wait is not yet registered, and the flow can then wait until timeout.
Saving the ID immediately narrows the window; it does NOT eliminate it.
Do not add a Delay, mark this "race safe", or imply every immediate result is
delivered. Do not replace it with Start and wait PLUS Create (two approvals).
The workshop deliberately retains the durable-ID split contract and exposes
this limitation. Production requires engineered service-state reconciliation.

Reconcile a suspected missed immediate response using the SAME saved ID:
1. Authorized operator records request ID, saved Approval ID, run ID, current
   status, create/save/wait times and selected user GUIDs in the approved support
   record. Use synthetic data in rehearsal; restrict run history access.
2. Open the same-cloud Power Automate Approvals portal under the authorized
   approval owner/operations identity and locate that exact approval. Match ID,
   not generic title alone. Inspect service status, response, responder and
   timestamps. If the portal does not expose the needed ID, use the tenant's
   approved supported administrative tooling/support path; do not guess.
   Standard approvals does not promise a universally available "Get approval
   details" action in this flow. This guide does not invent that action or grant
   broad access to internal approval tables.
3. If still awaiting response, retain ID and use an authorized recovery flow
   that waits on THAT existing ID, without any Create action. A second Wait is
   not proof it will replay an already-completed result; inspect service state.
4. If completed and request still Pending, validate the exact service outcome
   (Approve/Reject), identity and original selected-user membership with the
   same Entra-to-systemuserid rules as 51. Stop/coordinate the old run first so
   it cannot later expire/decide concurrently. Re-read Pending/same ID immediately
   before a controlled F-authorized status+Decided By+Comments-only update.
   Never spoof responder JSON into the normal flow or accept a forwarded email.
   Use an approved, audited reconciliation implementation; this is NOT a
   claim that the starter packages an automatic reconciliation worker.
5. A normal Wait timeout only means the flow received no completion. It does not
   prove the native service received no response. The baseline expiry branch's
   Pending/same-ID check prevents stale-ID/terminal overwrites but cannot
   distinguish a missed early response. Reconcile service state during the
   timing rehearsal and before treating such expiry as a business fact.
6. If baseline expiry already finalized the row despite a prior native decision,
   do NOT reopen it or edit its note. Escalate through approved business
   correction/audit procedures. Record the timing discrepancy externally.
   Do not silently mark UAT PASS. One successful timing trial does not prove the
   window impossible; this remains a documented non-production limitation.
